# Review: Helmsman — Autonomous Synthesis of Federated Learning Systems via Collaborative LLM Agents

## Summary
The paper proposes Helmsman, a LangGraph multi-agent system that turns a templated natural-language query into a Flower-based federated learning (FL) codebase. It works in three phases. (1) A planning agent with web search and RAG over FL literature drafts a plan, a reflection agent critiques it, and a human approves it. (2) A supervisor splits the plan into Task, Client, Strategy and Server modules, each built by a coder and tester agent pair. (3) The integrated code runs in a 5-round Flower simulation, and an evaluator agent (L1 crash check, L2 semantic check) and a debugger agent iterate for up to 10 attempts. The paper also introduces AgentFL-Bench, 16 FL tasks across 5 areas. On these, the generated solutions are compared with FedAvg, FedProx and one "specialized" method per task (Tables 2–4). The paper reports that Helmsman is competitive with and often better than the specialized methods, and that on Q16 (continual learning) it beats them by a large margin (51.04 vs 28.56). Full automation is reported on 62.5% of tasks.

## Strengths
- The problem is timely and practical: automating the composition of FL strategies is a plausible use of coding agents, and Flower provides an executable testbed.
- The L1/L2 diagnosis (crashes versus stagnant or divergent training) is a sensible, FL-specific feedback signal, and the modular decomposition mirrors FL architecture.
- The benchmark covers diverse FL settings (data, system, communication, personalization, active and continual learning) and is posed as natural-language queries. Results are given per task, not only as an average.
- The paper is honest that autonomy is limited: only 62.5% of tasks are fully automated, and the rest need human intervention.

## Weaknesses
1. **No agent baselines or ablations.** The paper claims the multi-agent design, hierarchical L2 diagnosis, RAG/web search, self-reflection and HITL are each important, yet none is ablated. The only comparisons are against FL algorithms, never against other code-generation or agent systems. Natural baselines are a single strong LLM (Claude-Sonnet-4) with the same prompt and tools, Claude Code or OpenHands, and an AI-scientist or AIDE-style system. Without them, it cannot be shown that the system and its components, as opposed to the base LLM, drive the results. The introduction's claim that single-agent approaches "exceed capacity" is unsupported.
2. **Human in the loop confounds the main results.** The planning stage requires human approval. The discussion states that harder tasks such as Q16 involve "collaborative plan refinement" and "human verification of the final synthesized code". It is unclear which rows in Tables 2–4 were produced fully autonomously and which with human help. Figure 4 suggests 6 of 16 tasks needed intervention, so the headline "competitive with hand-crafted baselines" mixes autonomous and human-assisted outputs. The nature, amount and expertise of the human input are not quantified. Human effort could account for much of the Q16 gain.
3. **Fairness of the comparison with "specialized" baselines.** The generated strategy is a hybrid of techniques that the LLM chose with access to the literature. The baselines appear to be single, off-the-shelf methods, and the main text gives no evidence of per-baseline hyperparameter tuning, nor of how many tuning trials each baseline or Helmsman received. Several baselines are loosely matched to their tasks (e.g., FedNova labelled for "distribution shifts"). Q7 and Q8 show the identical specialized value 63.62, which looks like a copy error. More importantly, Helmsman's output is the result of an iterative process whose selection criterion is unclear. If selection or iteration used test metrics, this is test-set leakage. The paper says the evaluator uses only 5-round training logs, but it does not specify whether human approval of the "final synthesized code" looks at final test accuracy.
4. **Results are weaker than the abstract suggests.** In Tables 2–4, Helmsman is best in about half of the tasks (Q3, Q5, Q6, Q7, Q9, Q10, Q11, Q16). It is clearly below the specialized method in Q1, Q2, Q4, Q8 (50.92 vs 63.62), Q12, Q13, Q14 and Q15 (68.59 vs 77.14). "Often superior" is overstated. The text for Q4–Q8 says it "outperforms a majority of the baselines", which is a weak criterion. Many differences are 0.1–1 point with no variance reported. Only Figure 4 mentions 3 runs; the performance tables report no seeds, no confidence intervals and no stated number of runs.
5. **Q16 is implausibly large and unexplained.** Accuracy of 51.04 on Split-CIFAR100 (5 tasks) with forgetting 0.07 is far above FedAvg (16.38), FedWeIT (28.56), FedLwF (30.94) and TARGET (34.89). The explanation, "client-side experience replay plus global model distillation", is a replay-based method. Replay buffers need stored data, which conflicts with the exemplar-free setting that the baselines (FedEWC, FedLwF, TARGET) respect. Without a replay-based FCL baseline, the comparison is apples to oranges. The generated code is not shown, so we cannot verify that it follows the privacy constraints or avoids leakage such as task identity. The paper presents this as "discovering novel algorithmic combinations", but replay plus distillation is a well-known recipe, so novelty is not demonstrated.
6. **Benchmark scope and metrics.** AgentFL-Bench has 16 tasks and no measure of agent quality beyond final accuracy: no per-task success rate or attempts table, no check of faithfulness to the specification, no cost (tokens, dollars, wall-clock), and no robustness across LLM backbones or seeds. The claim of "rigorous and reproducible" evaluation is not backed by a stated release of protocols. The benchmark is designed by the same group that built Helmsman, with no held-out tasks, and some "specialized" baselines (FedNS, FAST) seem to be the authors' own prior work. Tasks are mostly small image datasets, so the "system-level" claim is weak: every task is a Flower strategy plus a standard model.
7. **Thin evidence for the motivations.** The paper claims FL design is the "critical bottleneck" and that hand-crafted solutions are "brittle in dynamic environments". The experiments never test robustness to changing conditions (client count, resource variation), and no user study measures reduced engineering effort. "Deployment-ready" claims and the contrast with production frameworks (FATE, FLARE) are not tested at all; everything runs in a simulator.
8. **"Certified correct" claim.** The paper says the code is "autonomously certified as not only executable but also semantically correct". The L2 check consists of heuristics on 5-round logs (stagnation, zero participation, divergence), which cannot certify the semantic correctness of an aggregation algorithm. A method that silently degenerates to FedAvg would pass. There is no analysis of failure modes, of iteration statistics beyond Figure 4, or of cases where generated code ignores the plan.
9. **Presentation.** The tone is promotional ("new frontier", "significant step", "intractable"), and the Introduction and Related Work spend space on generic LLM-agent narratives. Section 6 is titled "Disucssion" (typo). Key experimental details (hyperparameters, baseline tuning, how the final strategy was selected, number of runs) are in appendix tables or absent. Generic baselines are only FedAvg and FedProx, although the motivation names stronger methods (SCAFFOLD, MOON, FedDyn).

## Questions
1. Which of the 16 results in Tables 2–4 were produced with no human intervention, and which with human plan refinement or code verification? Please report the human actions (number of feedback turns, what they changed) and show results with and without them.
2. How does Helmsman compare with a single-agent baseline (same LLM, tools and attempt budget) and with general coding agents (Claude Code, OpenHands, AIDE-like systems)? Please provide ablations removing RAG/search, reflection, the L2 check and modular decomposition.
3. How were baseline hyperparameters selected, and how many tuning runs did the baselines and Helmsman each receive? Was any model or code selection done using test accuracy?
4. For Q16, please show the generated code. Does it use a replay buffer of raw client data? If so, why is it compared with exemplar-free baselines, and how does it do against replay-based federated continual learning methods?
5. Please explain the identical 63.62 values for the specialized method in Q7 and Q8 and confirm the baseline numbers.
6. Please report means and standard deviations over seeds for Tables 2–4, plus cost (tokens, dollars, wall-clock) per task and success rates over repeated runs of the agent itself, since the system is stochastic.
7. Is AgentFL-Bench released (queries, baseline implementations, evaluation harness)? Are there held-out tasks not used when developing Helmsman's prompts?

- Presentation: 2
